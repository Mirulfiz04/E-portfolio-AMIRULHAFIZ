    Case study · final-year project

    How I built MEDS, and what it taught me.

    MEDS reads emotion from three signals: your face through the camera, your heart rate from a wearable sensor, and your voice. One Flutter app, a secure Supabase backend, two on-device ML models, and a CI/CD pipeline that tests and ships every change.

    • ~37klines of Dart
    • 20Flutter test files
    • 2on-device models
    • 6automated CI/CD jobs

    Hover or tap a part to see what it does.

    The ESP32 reads heart rate and SpO₂ and serves them over its own Wi-Fi hotspot. The app polls it, and a native Android channel pins that request to Wi-Fi so it still works while mobile data carries the internet.

    GitHub Actions. Every pull request runs CI; every merge to main also delivers.

    CI · in parallel
    Flutter analyze + tests
    Training-script self-checks
    Edge Functions type check
    iOS compile check (allowed to fail)
    CD · only if CI is green
    Build release APK
    Deploy Edge Functions
    • Flutter is pinned to one version so CI builds exactly what I build locally.
    • The Supabase CLI is pinned too. "latest" hit the GitHub API rate limit and broke a deploy, so I pinned a version that had deployed cleanly.
    • Secrets live in GitHub Actions secrets, never in the repo. The deploy job skips with a warning when the token is missing.

    Rule I designed around: the app is not trusted. The publishable key ships inside every APK, so anyone can call the API directly. Every rule that matters lives in the database or in an Edge Function.

    • Privilege escalation fixed. A trigger stops users changing their own role or status, so nobody can make themselves admin.
    • Blocking is real. Blocking a user in the admin panel now bans the account in Supabase Auth too, instead of only hiding the app’s start screen.
    • Faster policies. I rewrote RLS policies so auth.uid() runs once per query instead of once per row, and merged overlapping policies.
    • Indexes that match real queries, such as a user’s sessions sorted newest first.
    • Abuse limits. 30 AI calls and 10 emails per user per hour, counted in Postgres, with a 429 response above the limit.
    • The Claude API key stays server-side in an Edge Function. Security tests run against the live policies.
    • Found and fixed data leakage. My FER2013 copy merged several downloads, and about 75% of its test images also appeared in training. I wrote a script that dedupes faces and drops every test face from training, so the reported accuracy is honest.
    • Transfer learning on MobileNetV2 / V3, exported to TFLite and run on the phone, fed 224×224 face crops from ML Kit.
    • Personalisation. A webcam burst tool captures my own faces per emotion; they’re aligned with MediaPipe and split by capture order, so the test set holds photos the model has never seen.
    • Fusion. Face probabilities are smoothed over frames, then heart-rate change from a per-session baseline nudges them as an arousal signal, with hysteresis so the label doesn’t flicker. HR corroborates the face but never overrides a confident reading.
    • Voice check-in. A second model trained on RAVDESS and CREMA-D, tested on speakers it never heard, blends in for 20 seconds after you answer “Are you OK?”.
    • Training reports a confusion matrix, per-class F1, top-2 accuracy and ROC-AUC.
    1. Measure honestly before you optimise. A score measured on leaked test data looks great and means nothing. Fixing the split made the number trustworthy.
    2. Security belongs on the server. A check that exists only in Dart is a convenience, not security.
    3. Automate the boring, risky parts. CI catches breakages on every PR; CD means a merge is a release.
    4. Pin what you depend on. “latest” is a moving target that can break a build on a quiet day.
    5. Write the docs as you go. Backend, AI and training guides mean the next person (or future me) can run it.
    6. Know the limits. I listed what isn’t done yet: batched writes, data retention, staging, and SQL migrations in CI.
